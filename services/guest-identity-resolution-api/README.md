# Guest Identity Resolution API (AROYA Direct Guests, Phase 1)

This is the Python decision engine from *AROYA Direct Guest Identity Resolution Implementation Plan v2.1*, covering iterations 0 and 2.
It decides whether a direct Guest reuses an existing Global/Loyalty pair, gets a new one, or goes to manual review.
**Python never calls CRM.** The WSO2 Integration Service owns every CRM read and write, and Kafka consumption.
A test (`tests/unit/test_no_crm_client.py`) proves the service contains no CRM client, CRM endpoint or CRM credential.

## Rules (plan §12)
- **Direct scope** (CLIENT-APPROVED): source code ∈ {INT-ASSC, INT-CON, NEWINT-CON, MOBAPP, WHATSAPP, IN HOUSE} **and** agency name ∈ {AROYA CRUISES MAIN OFFICE [USD|EUR|GBP], FUTURE CRUISES, RIYADH SEASON, WHATSAPP}, compared exactly after trim and case-fold. INT-AGENT is out.
  Two owner decisions are still pending, and each is a config change: `GIR_DIRECT_ACCEPT_EMPTY_AGENCY` (default false) and adding `AROYA MAIN OFFICE SAR` to `GIR_DIRECT_AGENCY_NAMES`.
- **Precedence**: excluded → guardrail (100) → several distinct CERTAIN identities (conflict review) → one CERTAIN (reuse if committed, complete and active, otherwise pair repair) → four exact fields (review plus a provisional pair) → new permanent pair.
  The Jaro-Winkler/weighted shadow score is stored only and never changes the outcome (property-tested).
- **Normalization** (ASSUMPTIONS, tuned with baseline findings):
  - Names: NFKC, case-fold, approved punctuation.
  - DOB placeholders 1900-01-01, 1899-12-31, 0001-01-01, 1800-01-01. 1970-01-01 is a placeholder only when over-shared. Future dates and age > 120 are invalid.
  - Phones: both CRM **Mobile** (`phone`) and **Phone** (`alternatePhone`) are evidence.
    - `+`/`00` prefixes are international; `966XXXXXXXXX` without `+` becomes +966 (HIGH).
    - Otherwise the Guest's country, then citizenship, gives the context.
    - A Saudi `05…`/`5…` number without context is MEDIUM; anything else without context is LOW. MEDIUM and LOW are never evidence and never a forced +966.
  - E-mail placeholder list plus regex patterns.
  - Over-shared phone or e-mail: more than **5** distinct active identities, configurable; tune after baseline identity repair.

## Global ID / Loyalty ID generation: ported from the existing Mule logic
Source: Mule app `identity-support-exp-api`, flows `GET /generateGuestId` and `GET /generateLoyaltId`, called by `guest-identity-proc-api`, which the Ballerina service still calls today.
- **Global ID** = `UlidGenerator.generate()` → `de.huxhorn.sulky.ulid` 8.3.0 `nextULID()`: 26 Crockford-base32 characters with a time prefix. Today these start `01…`, matching the baseline's "2 leading digits + random alphanumerics".
- **Loyalty ID** = `"12"` + `randomInt(10000000)` zero-padded to 7 digits + a check digit = **10 digits**, matching the baseline's dominant shape (102,643).
  The check digit is the Mule DataWeave `luhnCheckDigit`, reproduced exactly. It doubles the **odd** positions of the reversed base, so it is **not** textbook Luhn (`aroya_check_digit` vs a standard validator differ, e.g. base 120000005 → 0, not 5). The client should confirm this is intended.
- **Uniqueness**: Mule checks none (a 10⁷ random space collides at a few thousand IDs by the birthday bound). The port re-draws when a keyed hash already exists (bounded attempts, metric `gir_pair_allocation_conflicts_total`), and UNIQUE constraints are the backstop.
  IDs that exist only in CRM are covered once the baseline is bootstrapped.
- **Existing-ID eligibility** (Mule rule, kept): a pair is reusable only when both IDs are present and the Global ID has no `-` (legacy UUID form).
  Global-only pairs are INCOMPLETE (MATCHED_IDENTITY_NOT_READY). One Loyalty ID under several Global IDs, or the reverse, makes **both** pairs CONFLICT (CURRENT_ID_MAPPING_CONFLICT).
- The legacy shapes found in the baseline (11-digit and `6-4` Loyalty IDs, 24–27-character Global IDs) are accepted as existing IDs. They are never generated.

## Build and deploy (prepared, not deployed to the customer environment)
- `Dockerfile`: python:3.12-slim pinned by digest, hash-locked dependencies, uid 10001, works with a read-only root filesystem. `sbom.cdx.json` is the CycloneDX SBOM.
- `deploy/helm/guest-identity-resolution-api`:
  - 2 replicas with readiness, liveness and startup probes;
  - non-root and a read-only filesystem;
  - Secret mounts for the DB password, CA, data key, HMAC key and service token;
  - NetworkPolicy: ingress only from the Integration (process-layer) pods and monitoring, egress only to DNS and the DB CIDR;
  - migration as a pre-install/pre-upgrade Job running as the schema owner;
  - ClusterIP only.
- DB connection is pure configuration (`GIR_DB_HOST/PORT/NAME/USER`, `GIR_DB_PASSWORD_FILE`, `GIR_DB_SSLMODE=verify-full`, `GIR_DB_SSLROOTCERT`, `GIR_DATABASE_SCHEMA`). See `docs/DB-READINESS-CHECKLIST.md`.

## Workbench support
These endpoints serve the Workbench through the Integration review API, all from PostgreSQL:
- `GET /v1/review-cases` (kind / status / assignee filters, paging, HIGH priority first, then SLA due time; SLA in business days, Sun–Thu, conflict 1 / four-field 2, configurable);
- `GET /v1/review-cases/{id}/history` (codes, states and user ids only);
- `POST /v1/review-cases/{id}/assignment` (taking a case yourself, or a supervisor handing it over);
- `POST /v1/review-cases/{id}/comments` (stored encrypted; text shown to reviewers and supervisors only).
